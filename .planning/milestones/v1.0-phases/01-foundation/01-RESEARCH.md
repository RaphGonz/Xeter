## User Constraints (from CONTEXT.md)

### Locked Decisions

**ID field strategy**
- `span_id` and `trace_id`: arbitrary strings — accept whatever the OTel SDK generates (typically 16-byte hex). No format constraint.
- `tenant_id`: UUID, generated at tenant creation time. Opaque, non-guessable, consistent FK target across PostgreSQL and ClickHouse.
- `flag_id` and `diagnostic_id`: UUID primary keys, generated by PostgreSQL (`gen_random_uuid()`).
- ID ownership: SDK generates `span_id` and `trace_id` at instrumentation time (OTel spec). Database generates `flag_id` and `diagnostic_id` on insert.

**Multi-tenancy enforcement**
- Primary layer: DAL/repository layer always injects `tenant_id` into every query.
- Fallback layer: PostgreSQL RLS as defense-in-depth against application bugs.
- Enforcement: DAL raises a Python exception before the query runs if `tenant_id` is missing — not a SQL error, a hard fail at the Python boundary. Must be covered by tests.
- ClickHouse: DAL-layer enforcement only (ClickHouse has no RLS). Same pattern — missing `tenant_id` raises immediately.
- RLS implementation: session variable pattern — `SET LOCAL app.current_tenant_id = ?` at the start of each transaction. Single app DB role; tenant_id injected per session. Compatible with asyncpg.

**Developer bootstrap**
- Dev tenant created via a seed script (`make seed` or `python seed.py`). Repeatable, deterministic, fast.
- Seed produces a fixed, well-known API key: `dev-api-key-local`. Hard-coded in seed script and `.env.example` so SDK test snippets are reusable.
- Registration endpoint (AUTH-05): single `POST /register` — creates tenant row, user row, hashes + stores API key, returns the plaintext key once. No email verification in Phase 1.
- Full reset: `make reset` tears down and recreates all DB schemas then re-runs the seed. Required for test isolation.

**Docker Compose ergonomics**
- Backend services run with hot reload via volume-mounted source code (`uvicorn --reload` or `watchfiles`). No image rebuild required for code changes.
- Port convention:
  - ClickHouse: 8123 (HTTP), 9000 (native)
  - PostgreSQL: 5432
  - Redis: 6379
  - MinIO: 9100
  - Analyser: 4317 (gRPC) / 4318 (HTTP, OTLP standard)
  - Presenter: 8000
  - View: 3000
- Startup ordering: `depends_on` with `condition: service_healthy` on all infrastructure services. Each infra service has a Docker healthcheck. App services don't start until dependencies are healthy.
- Frontend (View) runs inside Docker Compose. `docker compose up` starts the full stack — one command.

### Claude's Discretion

- ClickHouse MergeTree engine settings (partition strategy, TTL, async insert config) — use sensible defaults for dev
- Exact RLS policy SQL syntax and policy names
- Alembic vs raw SQL for migrations — Claude picks what fits best
- `.env.example` structure and variable naming
- Healthcheck intervals and retry counts for Docker

## Summary

Phase 1 establishes the entire infrastructure substrate that all subsequent phases build on. The work divides into four zones: (1) Docker Compose stack with correct healthcheck-gated startup ordering; (2) ClickHouse and PostgreSQL schemas that are locked before any data is written; (3) a DAL that enforces `tenant_id` at the Python boundary as primary control, backed by PostgreSQL RLS as defense-in-depth; and (4) the tenant registration endpoint plus dev bootstrap machinery.

The critical one-way door in this phase is the ClickHouse `ORDER BY (tenant_id, trace_id, time_begin)`. This key is baked into the MergeTree part sort order on first write. Changing it later requires a full table rebuild. The DAL tenant enforcement design is also permanent by intention — every service in every subsequent phase will import and use the same guard pattern established here.

The stack is entirely decided from the previous research. No exploratory choices remain. Python 3.12, FastAPI 0.135, SQLAlchemy 2.0 + asyncpg 0.31, Alembic 1.18, clickhouse-connect 0.15, passlib[bcrypt] for key hashing. The only discretion Claude has is in MergeTree engine settings, Alembic vs raw SQL for migrations, RLS policy syntax, healthcheck intervals, and Makefile targets.

**Primary recommendation:** Use Alembic for PostgreSQL migrations (not raw SQL) because schema evolution is certain across phases. Write the tenant guard as a base DAL class or decorator that all repository classes inherit/apply, making it impossible to forget.

### Pattern 1: Tenant Guard at the DAL Boundary

**What:** Every DAL method that touches a tenant-scoped table receives `tenant_id` as a required parameter. A guard function or base class checks at the Python layer — before any SQL is assembled — and raises `MissingTenantError` if `tenant_id` is `None` or empty.

**When to use:** Every query in the system. No exceptions. This is the primary isolation mechanism for ClickHouse (which has no RLS) and the application-layer check for PostgreSQL.

**Example:**
```python
# shared/dal/base.py
class MissingTenantError(RuntimeError):
    """Raised when a DAL method is called without a tenant_id."""
    pass

def require_tenant(tenant_id: str | None) -> str:
    """Call at the top of every DAL method that touches tenant-scoped data."""
    if not tenant_id:
        raise MissingTenantError(
            "tenant_id is required for all data access layer calls. "
            "This is a hard enforcement — do not catch this in application code."
        )
    return tenant_id


# shared/dal/tenants.py
from shared.dal.base import require_tenant

class TenantRepository:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def get_spans_for_trace(
        self, trace_id: str, tenant_id: str | None
    ) -> list[Span]:
        tid = require_tenant(tenant_id)  # Raises before any SQL
        result = await self.session.execute(
            select(Span).where(
                Span.tenant_id == tid,
                Span.trace_id == trace_id,
            )
        )
        return result.scalars().all()
```

### Pattern 2: PostgreSQL RLS with SET LOCAL Session Variable

**What:** After the Python-layer check, PostgreSQL RLS provides a second line of defense. At the start of every database transaction that touches tenant-scoped tables, set `app.current_tenant_id` using `SET LOCAL`. RLS policies reference this setting via `current_setting()`.

**When to use:** All PostgreSQL writes and reads via asyncpg in the Analyser, Worker, and Presenter services. The `SET LOCAL` scope means the setting is cleared when the transaction ends — safe with connection pools.

**Example:**
```python
# shared/db/postgres.py — transaction context manager
from contextlib import asynccontextmanager
from sqlalchemy.ext.asyncio import AsyncSession

@asynccontextmanager
async def tenant_session(session: AsyncSession, tenant_id: str):
    """Wrap a SQLAlchemy async session with RLS tenant context."""
    async with session.begin():
        # Set the RLS context variable for this transaction only
        await session.execute(
            text("SET LOCAL app.current_tenant_id = :tid"),
            {"tid": tenant_id}
        )
        yield session
        # COMMIT auto-clears SET LOCAL values
```

```sql
-- migrations/versions/001_initial.py (via raw SQL in Alembic migration)
-- Enable RLS on tenant-scoped tables
ALTER TABLE tenants ENABLE ROW LEVEL SECURITY;
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE api_keys ENABLE ROW LEVEL SECURITY;
ALTER TABLE flags ENABLE ROW LEVEL SECURITY;
ALTER TABLE diagnostics ENABLE ROW LEVEL SECURITY;

-- Create policies referencing the session variable
CREATE POLICY tenant_isolation ON tenants
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

CREATE POLICY tenant_isolation ON users
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

CREATE POLICY tenant_isolation ON api_keys
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

CREATE POLICY tenant_isolation ON flags
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

CREATE POLICY tenant_isolation ON diagnostics
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

**Critical caveat:** The `SET LOCAL` approach requires wrapping every operation in an explicit transaction. SQLAlchemy `AsyncSession` with `session.begin()` is the correct pattern. Autocommit mode bypasses `SET LOCAL` scope — never use autocommit on RLS-protected connections.

### Pattern 3: ClickHouse MergeTree Schema

**What:** The spans table is created with `ENGINE = MergeTree()` and `ORDER BY (tenant_id, trace_id, time_begin)`. This order is locked before any data is written. ClickHouse stores data physically sorted by this key, and the sparse primary index allows efficient prefix scans (tenant_id filter, then tenant+trace filter, then tenant+trace+time range).

**When to use:** Once, at infrastructure setup time. Never change after data is written.

**Example:**
```sql
-- executed via clickhouse-connect during Docker init or migration
CREATE TABLE IF NOT EXISTS spans (
    tenant_id       String,
    trace_id        String,
    span_id         String,
    parent_span_id  Nullable(String),
    time_begin      DateTime64(3, 'UTC'),
    time_end        DateTime64(3, 'UTC'),
    agent_name      String,
    agent_model     String,
    recipient       String,
    recipient_model Nullable(String),
    tool_name       Nullable(String),
    tool_description Nullable(String),
    tool_arguments  Nullable(String),   -- JSON inline, small payload
    tool_output     Nullable(String),
    available_tools_ref Nullable(String),
    prompt_ref      String,
    response_ref    String,
    raw_response_ref String,
    schema_version  String DEFAULT '1.0'
)
ENGINE = MergeTree()
ORDER BY (tenant_id, trace_id, time_begin)
SETTINGS index_granularity = 8192;
```

**Verifying index usage (EXPLAIN):**
```sql
EXPLAIN indexes = 1
SELECT span_id, agent_name, time_begin
FROM spans
WHERE tenant_id = '00000000-0000-0000-0000-000000000001'
  AND trace_id = 'abc123def456'
ORDER BY time_begin ASC;
-- Look for "PrimaryKey" and "Condition" lines showing the index was used
-- "Granules" count should be much smaller than total row count
```

### Pattern 4: Alembic Async Migration Setup

**What:** Initialize Alembic with `alembic init -t async migrations` to get the async-compatible `env.py`. Use raw SQL within migration scripts for DDL that Alembic can't autogenerate (RLS, custom triggers, ClickHouse).

**When to use:** All PostgreSQL schema changes from Phase 1 onward.

**Example:**
```bash
# Initialize once
alembic init -t async migrations

# Generate first migration (after defining SQLAlchemy models)
alembic revision --autogenerate -m "initial_schema"

# Run migrations
alembic upgrade head
```

### Pattern 5: API Key Generation and Storage

**What:** Generate a secure random API key, hash it with bcrypt via passlib, store only the hash. Return the plaintext key to the caller exactly once. Use a prefix convention (`xtr_`) to make keys recognizable in logs.

**Example:**
```python
# shared/dal/api_keys.py
import secrets
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def generate_api_key() -> tuple[str, str]:
    """
    Returns (plaintext_key, key_hash).
    Store only key_hash. Return plaintext_key to the user once and discard.
    """
    plaintext = f"xtr_{secrets.token_urlsafe(32)}"
    key_hash = pwd_context.hash(plaintext)
    return plaintext, key_hash

def verify_api_key(plaintext: str, stored_hash: str) -> bool:
    return pwd_context.verify(plaintext, stored_hash)
```

### Anti-Patterns to Avoid

- **Missing tenant_id silently ignored:** Never let a DAL method accept an optional `tenant_id` and proceed without it. The guard must raise, not skip.
- **SET LOCAL outside a transaction:** `SET LOCAL` only lasts for the current transaction. If you run it without `BEGIN`, it behaves like `SET SESSION` and leaks the tenant context to the next caller on the pooled connection. Always wrap in `session.begin()`.
- **RLS on migration connection:** The database user running Alembic migrations must have `BYPASSRLS` or be a superuser. Otherwise RLS blocks the migration runner from writing any rows. Use a separate privileged connection for migrations.
- **Bind-mounting database data directories on Windows/WSL2:** Permission errors are guaranteed. Use named Docker volumes (`pg_data`, `ch_data`, etc.) for all database storage.
- **ClickHouse ORDER BY as afterthought:** This must be set on table creation. Altering it requires dropping and recreating the table. Verify with EXPLAIN before writing any data.
- **Storing plaintext API keys:** Generate → hash → store hash → return plaintext once → discard. Never log or persist the plaintext.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password/key hashing | Custom bcrypt wrapper | `passlib[bcrypt]` | Timing-safe comparison, schema versioning, upgrade path to argon2 |
| Async PostgreSQL sessions | Manual asyncpg pool management | `SQLAlchemy 2.0 + asyncpg` via `create_async_engine` | Connection pooling, ORM mapping, transaction context managers all included |
| PostgreSQL schema versioning | Sequential `.sql` files run manually | Alembic | Downgrade support, autogenerate, version tracking in `alembic_version` table |
| Docker startup ordering | `sleep 5` hacks | `depends_on: condition: service_healthy` + healthchecks | Deterministic readiness; works regardless of machine speed |
| Tenant isolation enforcement | Call-site WHERE clauses | DAL guard + RLS | Forgetting one WHERE clause becomes a security incident without this |

**Key insight:** The tenant isolation layer is the most failure-prone custom code. The DAL guard + RLS combination means two independent systems must both fail before a cross-tenant leak is possible. Neither system is complex to build, but both must be built correctly at the start.

## Common Pitfalls

### Pitfall 1: SET LOCAL Leaking Tenant Context Across Pooled Connections

**What goes wrong:** `SET LOCAL app.current_tenant_id = 'tenant-A'` is run without an explicit transaction. The setting persists on the pooled connection and the next request using that connection gets Tenant A's data.

**Why it happens:** `SET LOCAL` only rolls back with a transaction rollback or commit. Without `BEGIN`/`COMMIT`, it is effectively `SET SESSION`.

**How to avoid:** Always use `async with session.begin()` wrapping the `SET LOCAL` call. SQLAlchemy's `AsyncSession.begin()` context manager handles commit/rollback automatically.

**Warning signs:** Integration tests where two sequential requests with different tenant_ids return the same data.

### Pitfall 2: RLS Blocking Migration Runner

**What goes wrong:** Alembic migration fails with "new row violates row security policy" when trying to insert seed data or reference data.

**Why it happens:** The database user running Alembic is subject to the RLS policies, but migrations need to insert rows without a tenant context.

**How to avoid:** The migration runner (and seed script) must connect as a PostgreSQL superuser or a role with `BYPASSRLS`. In local dev, the `postgres` superuser is fine. In production, use a dedicated `xeter_migrations` role with `BYPASSRLS`.

**Warning signs:** Migration fails immediately after `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`.

### Pitfall 3: ClickHouse ORDER BY Cannot Be Changed After Data Is Written

**What goes wrong:** Team writes test data into ClickHouse with the wrong ORDER BY, then decides to change it. Requires dropping and recreating the table, losing all data.

**Why it happens:** ClickHouse MergeTree physically sorts data on disk using the ORDER BY key during part creation. There is no ALTER TABLE to change it retroactively.

**How to avoid:** Run `EXPLAIN indexes = 1` on the expected query pattern before writing any data to verify the index is used correctly. Add this as a required verification step in the phase plan.

**Warning signs:** EXPLAIN output shows "Granules: N/N" (all granules scanned) instead of a fraction.

### Pitfall 4: MinIO Bucket Not Created Before Services Start

**What goes wrong:** Analyser or Worker starts, tries to PUT to MinIO, fails because the bucket doesn't exist.

**Why it happens:** MinIO starts the server with an empty state. It does not auto-create buckets.

**How to avoid:** Add a Docker Compose init container or `entrypoint` that creates the required bucket using `mc mb` or the MinIO Python SDK before any service that writes to S3 starts. Alternatively, create the bucket in the seed script.

**Warning signs:** Analyser logs `NoSuchBucket` errors on first S3 write.

### Pitfall 5: asyncpg and SQLAlchemy Event Loop Conflicts in Tests

**What goes wrong:** `pytest-asyncio` test fails with "no running event loop" or "event loop is closed" when using SQLAlchemy's `create_async_engine`.

**Why it happens:** asyncpg connections are tied to the event loop that created them. If the test creates a new engine per test and the loop is replaced between tests, connections become invalid.

**How to avoid:** Use `scope="session"` on the engine fixture. Use `anyio` as the pytest-asyncio backend. Set `asyncio_mode = "auto"` in `pyproject.toml` or `pytest.ini`.

**Warning signs:** Tests pass individually but fail when run as a suite.

### Pitfall 6: `gen_random_uuid()` Requires pgcrypto or PostgreSQL 13+

**What goes wrong:** Migration fails with "function gen_random_uuid() does not exist".

**Why it happens:** `gen_random_uuid()` is a built-in in PostgreSQL 13+. On PostgreSQL 12 or earlier it requires the `pgcrypto` extension.

**How to avoid:** The stack specifies PostgreSQL 16 (confirmed in STACK.md). This is not a concern for this project, but verify the Docker image is `postgres:16-alpine` and not an older version.

**Warning signs:** Migration error on `gen_random_uuid()` call.

## Code Examples

### Seed Script Pattern

```python
# scripts/seed.py
"""
Creates a deterministic dev tenant with a fixed API key.
Idempotent: safe to run multiple times.
Usage: python scripts/seed.py
"""
import asyncio
from passlib.context import CryptContext
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession

DEV_API_KEY = "dev-api-key-local"
DEV_TENANT_ID = "00000000-0000-0000-0000-000000000001"
DEV_EMAIL = "dev@xeter.local"

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

async def seed():
    engine = create_async_engine(DATABASE_URL)
    async with AsyncSession(engine) as session:
        # Run as superuser/BYPASSRLS — no SET LOCAL needed
        async with session.begin():
            # Upsert tenant
            await session.execute(text("""
                INSERT INTO tenants (tenant_id, name)
                VALUES (:tenant_id, 'Dev Tenant')
                ON CONFLICT (tenant_id) DO NOTHING
            """), {"tenant_id": DEV_TENANT_ID})

            # Upsert user
            pw_hash = pwd_context.hash("dev-password-local")
            await session.execute(text("""
                INSERT INTO users (tenant_id, email, password_hash)
                VALUES (:tenant_id, :email, :password_hash)
                ON CONFLICT (email) DO NOTHING
            """), {"tenant_id": DEV_TENANT_ID, "email": DEV_EMAIL, "password_hash": pw_hash})

            # Upsert API key
            key_hash = pwd_context.hash(DEV_API_KEY)
            await session.execute(text("""
                INSERT INTO api_keys (tenant_id, key_hash)
                VALUES (:tenant_id, :key_hash)
                ON CONFLICT DO NOTHING
            """), {"tenant_id": DEV_TENANT_ID, "key_hash": key_hash})

asyncio.run(seed())
```

### POST /register Endpoint

```python
# services/presenter/routers/auth.py
from fastapi import APIRouter
from pydantic import BaseModel, EmailStr
import uuid, secrets
from passlib.context import CryptContext

router = APIRouter()
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

class RegisterRequest(BaseModel):
    name: str          # Tenant name
    email: EmailStr
    password: str

class RegisterResponse(BaseModel):
    tenant_id: str
    api_key: str       # Returned once, never retrievable again
    message: str

@router.post("/register", response_model=RegisterResponse)
async def register(payload: RegisterRequest, session: AsyncSession = Depends(get_db)):
    tenant_id = str(uuid.uuid4())
    plaintext_key = f"xtr_{secrets.token_urlsafe(32)}"
    key_hash = pwd_context.hash(plaintext_key)
    pw_hash = pwd_context.hash(payload.password)

    # Run as BYPASSRLS connection — registration happens before tenant context exists
    async with session.begin():
        await session.execute(text(
            "INSERT INTO tenants (tenant_id, name) VALUES (:tid, :name)"
        ), {"tid": tenant_id, "name": payload.name})

        await session.execute(text(
            "INSERT INTO users (tenant_id, email, password_hash) VALUES (:tid, :email, :pw)"
        ), {"tid": tenant_id, "email": payload.email, "pw": pw_hash})

        await session.execute(text(
            "INSERT INTO api_keys (tenant_id, key_hash) VALUES (:tid, :kh)"
        ), {"tid": tenant_id, "kh": key_hash})

    return RegisterResponse(
        tenant_id=tenant_id,
        api_key=plaintext_key,
        message="Store this API key — it cannot be retrieved again."
    )
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Per-tenant PostgreSQL schemas (schema-per-tenant) | Single schema with `tenant_id` column + RLS | ~2022, driven by Supabase/Neon adoption | Simpler migrations, connection pooling works across tenants |
| Separate PostgreSQL roles per tenant for isolation | Single app role + RLS + session variable | ~2023 | Eliminates role explosion in connection pools; PgBouncer compatible |
| `clickhouse-driver` (community, native TCP) | `clickhouse-connect` (official, HTTP) | 2022 (ClickHouse Inc. released official driver) | Officially maintained; easier proxy/firewall compatibility |
| `alembic init` (sync template) | `alembic init -t async` | Alembic 1.7+ | Required for asyncpg; sync template causes event loop conflicts |
| Docker `depends_on` (starts process) | `depends_on: condition: service_healthy` + healthcheck | Docker Compose v2 | Eliminates race conditions where DB process starts but isn't ready |

**Deprecated/outdated:**
- `schema-per-tenant` multi-tenancy: operational nightmare at scale; avoid
- `clickhouse-driver` native TCP driver: use `clickhouse-connect` instead
- Sync Alembic template with async SQLAlchemy: use `-t async` flag

## Open Questions

1. **RLS policy and `POST /register`**
   - What we know: `POST /register` creates the tenant itself — there is no `app.current_tenant_id` to set at that point.
   - What's unclear: Should registration use a BYPASSRLS role, or should the `tenants` table have a permissive INSERT policy?
   - Recommendation: Use a dedicated `xeter_app` role with `BYPASSRLS` for the app connection. This is simpler than maintaining per-table exceptions for registration. The `SET LOCAL` tenant guard is applied on all subsequent requests after registration. During registration, no tenant context exists by definition.

2. **MinIO bucket creation**
   - What we know: MinIO does not auto-create buckets; S3 operations require a pre-existing bucket.
   - What's unclear: Best place to create the bucket — Docker Compose init container, seed script, or Presenter startup hook.
   - Recommendation: Create bucket in the seed script using `aioboto3`. This keeps all bootstrapping in one place and the seed script is already required for dev setup.

3. **ClickHouse schema initialization**
   - What we know: Alembic manages PostgreSQL. ClickHouse has no standard migration tool.
   - What's unclear: How to version ClickHouse DDL changes across phases.
   - Recommendation: Keep ClickHouse DDL as a single `deploy/clickhouse/init.sql` file that is mounted into the ClickHouse Docker container via `docker-entrypoint-initdb.d`. For Phase 1, the schema is simple enough that a single SQL file is the right choice. If the schema needs to change in later phases, evaluate `clickhouse-migrations` or track manually.

4. **RLS policy `current_setting()` missing key behavior**
   - What we know: If `SET LOCAL app.current_tenant_id` was never called on a connection and a query hits an RLS policy, `current_setting()` raises a "setting not found" error (unless called with `missing_ok = true`).
   - What's unclear: Whether this is the correct failure mode — should a missing tenant setting silently return no rows or raise loudly?
   - Recommendation: Use `current_setting('app.current_tenant_id', true)` with `missing_ok = true` in policies, which returns NULL when not set. The policy `USING (tenant_id::text = current_setting('app.current_tenant_id', true))` then returns no rows when tenant is missing. This is safer than erroring, since the DAL Python guard should have already caught the missing tenant before SQL is reached.
