Extend the list_spans function signature with four new optional Query parameters:

```python
flag_type: str | None = Query(default=None),
agent_name: str | None = Query(default=None),
from_time: str | None = Query(default=None),   # ISO 8601 timestamp
to_time: str | None = Query(default=None),      # ISO 8601 timestamp
```

Implementation:

1. **agent_name filter** — add `AND agent_name = %(agent_name)s` to the ClickHouse WHERE clause when provided. Simple ClickHouse column filter.

2. **from_time filter** — add `AND time_begin >= %(from_time)s` to the ClickHouse WHERE clause when provided. Parse the ISO string as-is (ClickHouse handles ISO timestamps natively).

3. **to_time filter** — add `AND time_begin <= %(to_time)s` to the ClickHouse WHERE clause when provided.

4. **flag_type filter** — this requires a two-step approach because flags live in PostgreSQL:
   a. After fetching span_ids from ClickHouse AND fetching flags from PostgreSQL, add an additional filter to the flags query: `Flag.flag_type == flag_type` when flag_type is provided.
   b. After merging, keep only spans that have at least one flag matching flag_type. Spans with no matching flag are excluded from the response.

The existing cursor and pagination logic remains unchanged. All filters are AND-combined. No filter = no WHERE clause change (backward-compatible).

Important: flag_type filtering happens POST-ClickHouse (filter on PostgreSQL flags result). agent_name and time filters happen IN the ClickHouse query. This means when flag_type is active, the final span count may be less than `limit` — this is acceptable for Phase 5. Optimization (pre-filter span_ids) is Phase 6 scope.

Run all existing spans tests PLUS the new filter tests to confirm GREEN.
