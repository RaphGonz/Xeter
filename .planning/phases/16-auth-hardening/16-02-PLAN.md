The runbook must contain all of the following sections:

**Overview**
- SECRET_KEY is loaded via `os.environ["SECRET_KEY"]` in both Presenter and Diagnosticer (no fallback). It is used to sign and verify HS256 JWTs. Access tokens expire after 30 minutes. Refresh tokens expire after 30 days.

**When to rotate**
- Suspected key compromise, routine rotation policy (e.g., quarterly), after a team member with prod access offboards.

**Option A: Simple rotation with 30-minute re-login gap (recommended)**
Step-by-step:
1. Generate new key: `openssl rand -hex 32`
2. Update `.env` (or secret manager): `SECRET_KEY=<new-value>`
3. Restart Presenter: `docker compose restart presenter` (or orchestrator equivalent)
4. Restart Diagnosticer: `docker compose restart diagnosticer`
5. Gap: All existing access tokens signed with the old key will fail verification immediately after restart. Users will see a 401 and must log in again. The 401 interceptor in the frontend will call `/api/auth/refresh` — but the refresh token is also signed with the old key, so that will fail too. Users must re-authenticate manually.
6. Duration of gap: up to 30 minutes (old access tokens), potentially up to 30 days (refresh tokens held by long-absent users). Accept the gap — it is the correct tradeoff for operational simplicity.

**Option B: Dual-secret window (zero-forced-logout rotation)**
Note: python-jose's `jwt.decode(token, secret, algorithms=[...])` accepts a single secret string — there is no built-in multi-secret mode for HS256 (unlike RS256 with JWKS). To implement a dual-secret window:

Step-by-step:
1. Add `OLD_SECRET_KEY = os.environ.get("OLD_SECRET_KEY")` to deps.py (temporary code change).
2. Wrap `verify_session_token` to try NEW key first, fall back to OLD key on JWTError:
   ```python
   try:
       payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
   except JWTError:
       if OLD_SECRET_KEY:
           payload = jwt.decode(token, OLD_SECRET_KEY, algorithms=[ALGORITHM])
       else:
           raise
   ```
3. Deploy this code change with both `SECRET_KEY=<new>` and `OLD_SECRET_KEY=<old>` set.
4. Wait 30 minutes (old access tokens expire). Wait 30 days if you want refresh tokens to naturally expire too, or force re-login.
5. Remove `OLD_SECRET_KEY` env var and the fallback decode code. Redeploy.

Recommendation: Use Option A for v1.3. Option B adds temporary code complexity. Use Option B only if zero forced re-authentication is a hard requirement.

**Service restart sequence**
Always restart in this order:
1. Diagnosticer (it does not issue tokens, so safe to restart first)
2. Presenter (issues tokens; once restarted, all new tokens use new key)

Reason: if Presenter restarts first, it may issue new tokens while Diagnosticer still has the old key — those tokens would be rejected by Diagnosticer briefly. Restarting Diagnosticer first avoids this window.
