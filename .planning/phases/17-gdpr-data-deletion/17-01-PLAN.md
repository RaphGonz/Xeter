Create xeter/scripts/delete_tenant.py following the operator script pattern from preflight_diagnoses_audit.py. The script must:

**CLI interface (argparse):**
- `--tenant-id` (required): UUID string for the tenant to delete
- `--confirm` (flag): Execute deletion; default is dry-run only

**UUID validation:**
Validate `--tenant-id` with `uuid.UUID(args.tenant_id)` before any DB connection. Print `ERROR: '...' is not a valid UUID.` and `sys.exit(1)` on ValueError.

**Dry-run phase (_count_all):**
Connect to all four stores and count affected data. Print a summary in this exact format:
```
Dry-run summary for tenant: {tenant_id}

  ClickHouse spans:         {n:,} rows
  PostgreSQL span_scores:   {n:,} rows
  PostgreSQL diagnostics:   {n:,} rows
  PostgreSQL diagnoses:     {n:,} rows
  PostgreSQL flags:         {n:,} rows
  PostgreSQL api_keys:      {n:,} rows
  PostgreSQL users:         {n:,} rows
  PostgreSQL tenants:       {n:,} rows
  S3 objects:               {n:,} objects  (prefix: {tenant_id}/)

  Redis (analysis_queue): ~{n} items  (transit queue — typically empty after processing)
  Redis flush procedure:
    If tenant spans are still queued (rare):
    1. Stop the Worker service: docker compose stop worker
    2. Inspect queue: redis-cli -a $REDIS_PASSWORD LRANGE analysis_queue 0 -1
    3. Remove matching span_ids one by one: redis-cli -a $REDIS_PASSWORD LREM analysis_queue 0 <span_id>
    4. Restart Worker: docker compose start worker
    NOTE: The analysis_queue is a short-lived transit queue. Spans are processed within
    seconds of ingestion. GDPR deletion is typically invoked after the tenant is inactive,
    making this queue empty.

DRY-RUN: No data deleted. Pass --confirm to execute.
```

**Redis count in dry-run:** Use the sync redis library to get the queue length — `redis.from_url(os.environ["REDIS_URL"]).llen("analysis_queue")`. Only use this for the count display; no items are removed. Wrap in try/except so Redis unavailability doesn't block the dry-run (print `~0 (Redis unavailable)` on error).

**Deletion phase (_delete_all), only runs when --confirm passed:**

Execute in this exact order:

1. ClickHouse: `client.command("ALTER TABLE spans DELETE WHERE tenant_id = %(tenant_id)s", parameters={"tenant_id": tenant_id})` — then print `  ClickHouse: mutation submitted (background — run dry-run again after 30s to verify count is 0)`

2. PostgreSQL: Use a single psycopg2 connection with `conn.autocommit = False`. Execute DELETE in child-before-parent order: span_scores, diagnostics, diagnoses, flags, api_keys, users, tenants. Use parameterised queries `%s` — never string interpolation. Call `conn.commit()` once after all DELETEs. Print each table as it completes: `  Deleted from PostgreSQL.{table}: {cur.rowcount} rows`.

3. S3: Use boto3.client("s3", endpoint_url=..., aws_access_key_id=..., aws_secret_access_key=...). Paginate with `s3.get_paginator("list_objects_v2")` using `Prefix=f"{tenant_id}/"`. Batch delete up to 1000 keys per call with `s3.delete_objects(Bucket=bucket, Delete={"Objects": keys})`. Print: `  Deleted from S3: {total_deleted} objects`.

After all deletions: Print `\nDELETION COMPLETE. Tenant {tenant_id} data removed from ClickHouse, PostgreSQL, and S3.`

**Idempotency:** Never treat "0 rows affected" as an error. DELETE WHERE on a non-existent tenant is a no-op — that is correct. Do not check for tenant existence before deleting.
